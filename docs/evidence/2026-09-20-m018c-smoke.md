# M018C evidence — five-task smoke with the pinned model in the loop

Date: 2026-09-20 (Australia/Sydney). Stage: M018C (screenshot-driven loop).
Model: pinned Qwen3.5-4B (Q4_K_M, llama.cpp, thinking off, ctx 4096), schema-
constrained action decoding. Cost discipline: five initial runs (one per
frozen smoke task) plus one recorded iteration of task 11 after the single
inspected failure class; no repeated batches.

## Results (initial runs)

| Task | Outcome | Actions | Calls | Time | Notes |
|---|---|---|---|---|---|
| 01 | **finished** | 0 | 0 | 0.9 s | Already satisfied: the fixture redirect lands on `/news/`; the oracle passed before any model call (infrastructure demonstration). |
| 11 | blocked:recovery_exhausted | 3 (refused) | 3 | 17.2 s | Model emitted `{"action":"type","text":"AI"}` three times without clicking the field first; `refused_focus` each time; recovery cap stopped it. |
| 21 | failed:finish_unverified | 1 | 1 | 6.3 s | Model called `finish` directly from the news list with a wrong answer (never opened a story, so no story code). |
| 41 | blocked:no_progress | 2 | 2 | 12.6 s | Clicked the same point (374,600 px) twice with no page change; the identical-outcome guard blocked. |
| 31 | blocked:recovery_exhausted | 3 (refused) | 3 | 14.6 s | Same type-first class as 11. |

Productive completion (independent oracle): **1/5** — the already-satisfied
task. Every guard behaved exactly as frozen: refusals fed back as neutral
history, two-recovery cap, identical-outcome block, fail-closed throughout,
zero unintended clicks outside the disposable browser.

## Failure classes (inspection order)

1. **Type without focus (11, 31).** The model expressed the goal ("search
   for AI") as text entry and never clicked the input first; after each
   refusal it repeated the same action. Per the frozen protocol, exactly one
   change followed this inspection: prompt v2 added "click the field first"
   and "do not repeat a refused action" (recorded in
   `task-11-attempt2.json`; the model still repeated — the class persists).
2. **No spatial targeting / no adaptation (41).** Identical clicks with no
   page change; nothing in the loop authorizes acting on unverified
   positions, so this is a model-planning failure, not a loop failure.
3. **Premature finish (21).** The model answered without gathering the
   evidence the task requires (story code). The oracle refused the claim.

## Vision pipeline verification (attribution check)

A diagnostic one-call probe (`scripts/m018c_vision_probe.py`, output below)
confirmed the screenshot really reaches the model through the loop's own
pipeline (2560×1440 → 1280×720 model view):

```
full : 396420 bytes, 2560 x 1440 scale 2.0
model: 82881 bytes, 1280 x 720
first_ms: 2198.0 complete_ms: 2373.3
model says: {"page": "Search", "input": "query"}
```

The model correctly identified the page and the search input. The smoke
failures are therefore planning/grounding limitations of this 4B model, not
a broken image path.

## Interpretation (honest boundaries)

- The measured smoke result is **1/5 productive** (zero after the already-
  satisfied case): the pinned 4B model cannot yet drive the screenshot-only
  loop on these tasks. That is the finding, and it is exactly what this
  stage was for.
- No change was made beyond the one post-class fix the protocol allows
  (prompt v2, recorded). The remaining classes are development work for
  M018D on the 30 development tasks — where the plan permits iteration —
  before the held-out set runs once.
- The loop, adapter, guards, oracles, and evidence plumbing all worked as
  designed; nothing was tuned to make numbers look better, and no task was
  re-run to improve its outcome.
